Claude Code 支持通过 Anthropic 兼容接口接入 GLM 等第三方模型：工具调用、权限模型保持不变，只换推理后端。本文用两个互补场景走一遍完整流程——从零搭建基于 Arthas 的 JVM 智能诊断 Agent，以及在百万级数据的订单系统里治理慢查询。

<!-- more -->

## 背景：为什么要换后端模型

已经搭好 Claude Code 工作流的团队，常有成本或合规上的考量，不能使用默认模型。部分服务商会提供 Anthropic 兼容接口，配合环境变量即可把请求路由到自己的模型。

需要先建立两个认知：

- **接入方法不绑定具体模型**：以 GLM-5.1 为例记录的流程，在后续版本或其他兼容模型上同样适用。
- **兼容不等于等价**：兼容程度、可用功能和数据处理方式由服务商决定，不能默认与官方模型完全一致，能力边界要靠任务验证。

选这两个场景，是因为它们正好覆盖 AI 辅助编程的两种典型模式：场景一是"从 0 到 1"的工程交付，考验规划与批量编码能力；场景二面对既有代码库做增量优化，考验对旧架构的理解能力。

## 上手：接入与配置

整体三步：先安装 Claude Code 本体；再用 cc-switch 这类工具统一管理多家模型的切换；最后按模型提供方的文档，完成 Claude Code 内部模型环境变量与目标模型的对应配置。配置完成后建议先发一个只读小任务（比如"读一下项目结构并说明各模块职责"）确认路由生效。

如果更习惯图形界面，也可以用 VS Code + Claude Code 插件做对话与代码审查，验收 diff 比纯终端直观。

## 场景一：从零搭建 JVM 智能诊断 Agent

### 任务动机

JVM 线上诊断的传统路径基本固定：看 Grafana 面板定位方向，登录服务器查 CPU、内存、GC，再启动 Arthas 逐步缩小范围。这条路线的痛点在于：监控指标繁多、依赖主观推断；排查链路跨多个工具、紧急故障时低效；Arthas 指令强大但门槛高，要求熟悉参数与推理路径。工程化的构想是：把诊断经验整理成可审计的步骤链，让 AI 根据故障现象执行只读诊断流程、收集证据、生成候选原因。

### 交付过程

完整的需求描述（含技术选型、架构设计、表设计、部署架构的要求）直接决定了方案质量。AI 没有立刻写代码，而是先产出分阶段技术方案与三层架构图：用户层输入服务名与故障现象，Agent 层由 Skill 引擎、Arthas HTTP Client 与 AI 分析引擎协同，底层通过 Arthas HTTP API 对接目标实例。方案确认后再下达开发指令，最终生成 9 个模块、46 个文件的候选实现，Skill 引擎内置 7 个覆盖常见故障场景的诊断技能（CPU 飙高、OOM、死锁、慢接口等），依赖层级按 common → model → dal → client → skill → ai → service → web → bootstrap 划分。

一个实用技巧：需要集成现成组件时（这里是 Spring AI Alibaba 的 Agent Chat UI），直接给官方文档链接，比详细描述需求更高效。

本地验证用一个死循环的 CPU 测试接口：Agent 先取 Dashboard 概览，再按线程栈定位代码，用 jad 输出反编译结果，最后生成诊断报告。报告是待复核结论，不能仅凭它处置线上故障。

## 场景二：百万级数据下的慢查询治理

既有订单服务（Spring Boot + MyBatis）灌入百万级测试数据后，"关键词模糊匹配 + 时间区间 + 金额过滤"的搜索接口耗时 18375ms。把慢查询日志直接丢给 AI，它结合 SQL 与表结构给出分阶段方案：

- **数据库层**：ngram 全文索引替代 `LIKE '%xxx%'` 全表扫描，另加复合索引与覆盖索引共 5 个候选；
- **应用层**：查询语义迁移到 `MATCH ... AGAINST`；offset 超过初始阈值 1000 时自动切换延迟关联（先用覆盖索引子查询定位主键再回表）；默认不查总数，显式传参才执行 COUNT。

改完预热后单次请求降到 300ms 以内，约快 60 倍。但单次前后截图不构成可复现结论——索引是否有效取决于最左前缀与过滤选择性，阈值 1000 也只是初值，正式结论需要 `EXPLAIN ANALYZE`、不同 offset 的分档压测和 p95/p99 报告。

## 分析与思考

**做得好的地方**：需求进、方案出，能快速形成评审材料；数据库与应用两层的优化同步推进，覆盖全面；给出的阈值等参数可作为基准测试的起点。

**必须人工兜住的边界**：

- **生产安全要单独设计**：Arthas 的 watch、trace 属于字节码增强，不能当普通只读查询。诊断 Agent 进生产前，认证、实例白名单、命令白名单、高风险操作审批、限流与审计缺一不可，模型生成的字符串绝不能直接拼成命令执行。
- **长链路会断**：复杂持续编码任务中，AI 后半程可能遗忘前面的设计约束，复杂任务要拆成明确阶段、逐阶段确认。
- **取舍不替你做的**：全文索引还是 ES、延迟关联还是游标分页，AI 列方案但不替你权衡，需要结合业务场景判断；生成代码与团队规范的契合度也要磨合。

## 小结

- Claude Code 接第三方模型只换推理后端，工程任务仍依赖清晰的诊断数据与分阶段验收。
- 两个场景分别验证了"从 0 到 1 交付"与"既有系统增量优化"两种模式，前者重规划评审，后者重证据与压测。
- AI 负责缩短"从想法到候选实现"的距离；安全边界、方案权衡与最终验收，仍要由懂业务的人把关。
