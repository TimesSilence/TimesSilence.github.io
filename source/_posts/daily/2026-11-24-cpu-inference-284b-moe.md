11 月中旬，开源项目 [llama-modchip](https://github.com/synchopate/llama-modchip) 登上 Hacker News 热榜：把 284B 参数的 DeepSeek-V4-Flash 压进 64GB DDR5 内存、零 GPU 纯 CPU 跑出每秒约 10 个 token。这不是魔法，而是把容量、带宽、精度三本账算到了字节级。本文讲清这三本账怎么算，以及如何用它估算任意模型在你机器上的可行性。

<!-- more -->

## 问题/矛盾

「本地跑大模型」的劝退公式人人会背：模型参数 × 每参数字节数 = 所需显存。284B 参数按 FP16（每参数 2 字节）算是约 569GB，得一台插满 A100 的服务器。于是结论似乎是：没有高端 GPU 就别碰大模型。

但这个公式掩盖了真正的矛盾。大模型推理的瓶颈其实有两个，而且都和「算力」无关：

1. **容量墙**：权重必须完整驻留内存，少一个字节模型就加载不起来；
2. **带宽墙**：自回归解码每生成一个 token，都要把「用到的权重」从内存完整读一遍，读取速度直接给 tok/s 封了顶。

CPU 的浮点算力反而不是主要矛盾——解码阶段的矩阵乘是典型的「访存密集型」负载，算术强度极低，计算单元大部分时间在等数据。想突破，就得同时回答三个问题：怎么装下、怎么读快、精度损失怎么控制。

## 技术解析

### 容量账：MoE 改变的是「读多少」，不是「存多少」

DeepSeek-V4-Flash 是混合专家（MoE）架构：总参数 284.33B，43 层 MLA 注意力，每层 256 个路由专家加 1 个共享专家，但每个 token 只激活约 13.17B 参数（约 4.6%）。

这里有个容易搞反的点：**MoE 的稀疏性节省的是计算和带宽，不是存储**。路由专家再多，推理前谁也不知道会用到哪个，284B 参数必须一个字节不落地躺在内存里。所以容量账只能向「每个参数占几位」要空间。

### 量化账：从 16 位压到 1.71 位

量化的本质是给每个权重用更少的比特编码。按 284.33B 参数算笔账：

```text
FP16（16 bit/权重）：284.33B × 2 B   ≈ 569 GB
INT8（8 bit/权重）： 284.33B × 1 B   ≈ 284 GB
1.71 bit/权重：     284.33B × 1.71/8 ≈ 60.8 GB ≈ 56.6 GiB
```

llama-modchip 的做法是基于补丁版 llama.cpp，用自研的 Fractal-64 / LUT-VQ3-64 矢量量化方案把权重重新转码到平均 1.71 bpw（bit per weight），最终 GGUF 文件 56.56 GiB。这个数字的选取很讲究：作为对照，Unsloth 的 UD-IQ1_S 构建是 76.87 GiB，超过 64GB Linux 主机约 62.5 GiB 的实际可用上限；56.56 GiB 则给操作系统、KV 缓存和运行时留出了余量。项目方实测 256K 上下文下常驻内存稳定在 57.6–58.9 GiB，零 swap——一旦 swap，磁盘带宽会让速度直接崩掉，所以「刚好不 swap」就是容量账的红线。

### 带宽账：解码速度的天花板是算出来的

解码阶段每生成一个 token，需要读取的数据 ≈ 本 token 激活的权重。按 13.17B 活跃参数、1.71 bpw 估算：

```text
每 token 读取量 ≈ 13.17B × 1.71 / 8 ≈ 2.8 GB
消费级 DDR5 双通道有效带宽 ≈ 60–80 GB/s
理论解码上限 ≈ 带宽 / 每 token 读取量 ≈ 20–28 tok/s
```

项目方在 16 核 Zen 5（Ryzen 9 9955HX）+ 64GB DDR5 上的自测数据：未打补丁的 UD-IQ1_S 基线 5.91 tok/s，优化后无损解码 9.06–9.95 tok/s。与理论上限的差距来自 KV 缓存读取、专家路由调度和访存局部性损耗——这也正是它另外两个优化的方向：预填充内核做 CPU 缓存分块（cache tiling），把数据按 L1–L3 缓存层次切块调度，缓存命中时预填充达 44.36 tok/s；解码侧挂一个仅 1.64MB 的 n-gram 草稿器做投机解码，用小草稿一次猜多个 token、大模型并行验证，把解码推到 11.5–14.7 tok/s。

需要冷静看待的是：这些数字均来自项目方单机自测，且「质量损失小」的对照对象是已压到 1 bit 量级的版本，而非原始精度模型。1.71 bpw 属于极端量化区间，能力折损必然存在，幅度只能按自己的任务实测。

## 实践

想在本地复现或评估类似方案，一个可迁移的估算流程是：

```bash
  # 1. 容量：模型能否装下？
  #    可用内存 × 0.9 > 总参数量 × bpw / 8 + KV缓存 + 运行时(约2-4GB)
  # 2. 速度：解码能跑多快？
  #    理论 tok/s ≈ 内存有效带宽 / (激活参数 × bpw / 8)
  # 3. 实测验证（以 llama.cpp 系为例）
llama-cli -m model.gguf -p "你的测试提示" -n 128 --temp 0
```

三条经验性的判断标准：

- **MoE 模型是 CPU 推理的唯一甜点**。稠密模型的「激活参数 = 总参数」，带宽账直接按全量算，7B 以上的稠密模型在 DDR5 上就已慢得难受；MoE 才能用「大总参数、小激活参数」的组合同时赢容量面和能力面。
- **先查内存通道数再查容量**。同样是 64GB，双通道 DDR5 与四通道/八通道平台的有效带宽差数倍，tok/s 近似线性跟随后者。
- **按场景匹配预期**。10 tok/s 上下适合离线批处理、代码审查、隐私数据整理这类「发起后不用盯屏」的任务；交互式对话需要 30 tok/s 以上才不烦躁，这不是当前 CPU 方案能满足的。

## 对比与权衡

| 维度 | 本地 CPU + 极端量化 | 本地 GPU | 云端 API |
| --- | --- | --- | --- |
| 硬件门槛 | 64GB 内存工作站 | 数百 GB 显存 | 无 |
| 速度 | ~10 tok/s | 数十 tok/s | 高且稳定 |
| 数据隐私 | 完全本地 | 完全本地 | 出域 |
| 精度 | 1.71 bpw，有损 | 可跑高精度 | 原始精度 |
| 边际成本 | 电费 | 电费 | 按 token 计费 |

更有迁移价值的是方法论：评估任何「大模型能不能在这台机器上跑」的问题，先算容量账（装不装得下、留不留得出 KV 缓存），再算带宽账（解码上限是多少），最后才轮到算力账。MoE 架构把推理的主要矛盾从算力搬到了内存子系统，这意味着内存带宽——而非 TOPS——正在成为端侧 AI 硬件的核心指标。

## 小结

- MoE 的稀疏激活省的是计算与带宽，不省存储；容量账只能靠量化压 bpw。
- 284B × 1.71 bpw ≈ 56.6 GiB，是贴着 64GB 可用内存红线算出来的工程数字。
- 解码 tok/s 由「内存带宽 ÷ 每 token 活跃权重量」封顶，缓存分块与投机解码是在逼近这个上限。
- 极端量化的精度折损没有权威结论，所有自测数据都要按自己的任务复核。
- 本地 CPU 推理的定位是隐私敏感、可离线的异步任务，不是云端低延迟交互的替代品。
